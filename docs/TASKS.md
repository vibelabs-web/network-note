### [x] Task 2.1: MongoDB 스키마 설계 및 구현

**목표**: 메모와 연결 데이터를 저장하기 위한 MongoDB 컬렉션 스키마를 설계하고, Pydantic 모델을 정의한다.

**전제 조건**: Task 1.2 완료

**참조 문서**:
| 문서 | 섹션 | 내용 |
|-----|------|------|
| PRD | 4. 데이터 모델 | Memo, Connection 인터페이스 정의 |

| DB Design | 4. 인덱스 전략 | 모든 인덱스 정의 |
| DB Design | 부록 A. 데이터 검증 규칙 | 필드별 검증 규칙 |
| DB Design | 부록 B. Zettel ID 생성 규칙 | ID 생성 로직 |

**데이터베이스 스키마**:

**메모 컬렉션 (memos)**:
```python
{
  "_id": ObjectId,                    # MongoDB 자동 생성 ID
  "zettelId": String,                 # 제텔카스텐 ID (예: "2024-12-25-001")
  "title": String,                    # 메모 제목 (필수, 최대 200자)
  "content": String,                  # 마크다운 내용 (필수)
  "createdAt": DateTime,              # 생성 시간 (필수, 자동 생성)
  "updatedAt": DateTime,              # 수정 시간 (필수, 자동 업데이트)
  "connections": [                    # 연결 목록 (배열)
    {
      "targetId": ObjectId,           # 연결 대상 메모 ID
      "type": String,                 # "explicit" 또는 "suggested"
      "strength": Float,              # 연결 강도 (0.0 ~ 1.0)
      "createdAt": DateTime           # 연결 생성 시간
    }
  ],
  "mentions": [String],               # @멘션된 메모명 목록 (배열)
  "tags": [String],                   # 태그 목록 (배열, 소문자로 저장)
  "connectionCount": Integer          # 연결 수 (인덱싱 및 정렬용, 자동 계산)
}
```

**인덱스**:
- `zettelId`: 유니크 인덱스 (중복 방지)
- `title`: 텍스트 인덱스 (검색용)
- `tags`: 다중 키 인덱스 (태그 필터링용)
- `createdAt`: 내림차순 인덱스 (최신순 정렬용)
- `connectionCount`: 내림차순 인덱스 (연결 수 정렬용)
- `updatedAt`: 내림차순 인덱스 (최근 수정순 정렬용)

**작업 내용**:
1. Pydantic 스키마 정의
   - `backend/app/schemas/memo.py` 파일 생성
   - `MemoCreate`: 메모 생성용 스키마 (title, content, tags)
   - `MemoUpdate`: 메모 수정용 스키마 (모든 필드 선택적)
   - `MemoResponse`: 메모 응답용 스키마 (모든 필드 포함)
   - `Connection`: 연결 객체 스키마
   - 각 스키마에 적절한 검증 규칙 추가 (길이 제한, 타입 검증)

2. MongoDB 모델 정의
   - `backend/app/models/memo.py` 파일 생성
   - 메모 문서 구조 정의
   - 인덱스 생성 함수 작성
   - 연결 수 자동 계산 로직

3. Zettel ID 생성 유틸리티
   - `backend/app/utils/zettel_id.py` 파일 생성
   - 날짜 기반 고유 ID 생성 함수
   - 형식: `YYYY-MM-DD-XXX` (XXX는 해당 날짜의 순번)
   - 중복 체크 로직 포함

4. MongoDB 인덱스 초기화
   - `backend/app/services/mongo_service.py`에 인덱스 생성 함수 추가
   - 애플리케이션 시작 시 자동으로 인덱스 생성

5. 스키마 검증
   - 각 스키마가 올바르게 정의되었는지 확인
   - 필수 필드와 선택 필드 구분 확인

| 문서 | 섹션 | 내용 |
|-----|------|------|

| PRD | 2.1.3 AI 기반 연결 제안 | 제안 승인/거부 요구사항 |

| Flowchart | 연결 승인/거부 플로우 | 제안 처리 흐름 |

**작업 내용**:
1. 연결 제안 API (`GET /api/memos/{memo_id}/suggestions`)
   - 경로 파라미터: `memo_id` (제안을 받을 메모)
   - 쿼리 파라미터:
     - `limit`: 제안 개수 (기본값: 10, 최대: 20)
     - `threshold`: 유사도 임계값 (기본값: 0.5)
   - 해당 메모의 임베딩 가져오기
   - ChromaDB에서 유사한 메모 검색
   - 이미 연결된 메모는 제외
   - 자신은 제외
   - 유사도 점수 기준으로 정렬
   - 응답 형식:
     ```json
     {
       "suggestions": [
         {
           "memoId": "string",
           "title": "string",
           "zettelId": "string",
           "similarity": 0.85,
           "reason": "벡터 유사도 기반 제안"
         }
       ]
     }
     ```

2. 제안 승인 API (`POST /api/suggestions/approve`)
   - 요청 본문:
     - `sourceId`: 제안을 받은 메모 ID
     - `targetId`: 제안된 메모 ID
   - 명시적 연결로 변환 (type: "explicit")
   - 양방향 연결 생성

3. 제안 거부 API (`POST /api/suggestions/reject`)
   - 요청 본문:
     - `sourceId`: 제안을 받은 메모 ID
     - `targetId`: 거부할 메모 ID
   - 거부 기록 저장 (선택사항, 향후 같은 제안 방지용)

4. 배치 제안 생성 함수
   - 여러 메모에 대한 제안을 한 번에 생성
   - 백그라운드 작업으로 실행 가능

**검증 기준**:
- 제안 API가 정상적으로 동작하는지 확인
- 제안된 메모가 실제로 유사한지 확인 (수동 검증)

- 제안 승인 시 연결이 정상적으로 생성되는지 확인
- 유사도 점수가 적절한 범위인지 확인

   - 3단계: 최종 점수 계산 (벡터 유사도 + LLM 점수 가중 평균)
   - 4단계: 최종 제안 목록 반환

2. 제안 API 업데이트 (`GET /api/memos/{memo_id}/suggestions`)
   - 쿼리 파라미터 추가:
     - `useLLM`: LLM 재평가 사용 여부 (기본값: false)
   - `useLLM=true`일 때 하이브리드 방식 사용
   - `useLLM=false`일 때 벡터 검색만 사용

3. 비동기 제안 생성 API (`POST /api/suggestions/refine`)
   - 요청 본문:
     - `memoId`: 제안을 받을 메모 ID
     - `candidateIds`: LLM으로 재평가할 후보 메모 ID 목록

   - 완료 시 결과 반환

5. 캐싱 전략
   - LLM 평가 결과 캐싱 (같은 메모 쌍은 재평가하지 않음)
   - Redis 또는 인메모리 캐시 활용
